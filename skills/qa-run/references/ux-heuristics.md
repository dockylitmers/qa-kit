# 화면 UX 점검표 — 단순하고 직관적인가

화면이 범위에 있는 실행(모드 device·both, 또는 화면 코드를 읽는 code)에서 쓴다. 장애 중심 순위는 그대로다. 이 표는 **사람이 길을 잃거나 잘못 알아듣는 화면**을 찾는 데 쓰고, 찾은 것은 4절대로 결함·변경 요청·취향으로 가른다. 기준 문장은 하나다: **처음 보는 사람이 설명 없이, 망설임 없이 끝낼 수 있는가.**

## 1. 근거 원칙 (요약, 원문은 5절)

### 토스 제품 원칙 (공통 상위 가치: 단순함 — 배우지 않아도 이해되는 상태)
공식 글은 단순함과 "한 화면에서 할 일은 하나"를 직접 말한다(5절 S2). 아래 이름 목록은 책 『유난한 도전』을 요약한 2차 글로만 확인했다(S9).

| 원칙 | 화면에서 보이는 모양 |
|---|---|
| One thing per one page | 한 화면에 메시지 하나, 주요 버튼 하나 |
| Easy to answer | 화면이 묻는 질문에 몇 초 안에 답할 수 있다. 기억하기 어려운 값은 시스템이 채운다 |
| Value first, cost later | 가치(가격·결과)를 먼저 보여 주고 로그인·입력·인증은 뒤로 미룬다 |
| Tap & scroll | 핵심 흐름이 탭과 세로 스크롤로 끝난다(가로 스와이프·길게 누르기에 기대지 않음) |
| Casual concept | 전문 용어 대신 일상어 |
| Minimum features · Less policy | 목표에 꼭 필요한 기능만, 쓰기 전에 알아야 할 조건은 최소로 |
| Context-based | 지금 사용자의 맥락에 맞는 흐름 |
| No more loading | 기다리게 하지 않는다 |
| No ads patterns | 광고형 배너가 아니라 기능으로 이끈다 |

### 토스 라이팅 원칙 (공식, S1)
가치: 명확·간결·친근·존중·공감. 8원칙을 점검 질문으로 바꾸면:
1. 이 버튼·문구로 다음 화면을 예상할 수 있나(Predictable hint)
2. 빼도 뜻이 같은 단어가 있나(Weed cutting)
3. 정보 없는 문장이 있나(Remove empty sentences)
4. 가장 중요한 메시지 하나만 남았나(Focus on key message)
5. 어려운 말 없이 말하듯 쓰였나, 한 문장에 한 메시지인가(Easy to speak)
6. 강요하거나 겁주지 않고 제안하나(Suggest over force)
7. 누구나 이해하고 누구에게도 해롭지 않은 말인가(Universal words)
8. 사용자의 감정을 헤아렸나(Find hidden emotion)

토스 개발자 문서의 문구 규칙(S4): 해요체, 능동형("했어요"), 긍정형, 과한 높임 피하기, 대화상자의 거절 버튼은 "닫기"(하던 일이 취소되는 것처럼 들리는 "취소"를 피함), 결과를 알 수 있는 버튼 이름.
같은 문서가 금지하는 다크 패턴: 들어가자마자 뜨는 시트, 뒤로 가기를 막는 시트, 거절할 길이 없는 버튼, 예상 못 한 전면 광고, 결과를 알 수 없는 버튼 이름. 그래픽은 실제 상태와 맞아야 한다(오류가 없는데 경고 아이콘, 기다릴 일이 없는데 로딩 애니메이션 금지).

### 일반 원칙
- NN/g 10 휴리스틱(S10): 상태가 보임, 사용자의 말, 나갈 길, 일관성, 오류 예방, 기억보다 알아보기, 효율, 군더더기 없음, 오류에서 회복, 도움말.
- Laws of UX(S13): 선택지가 많을수록 결정이 느리다(Hick), 작고 먼 대상은 누르기 어렵다(Fitts), 사람들은 다른 앱에서 익힌 방식을 기대한다(Jakob), 400ms 넘는 반응은 흐름을 끊는다(Doherty), 끝이 가까워 보이면 더 끝까지 간다(Goal-gradient).
- 플랫폼: 탭 바는 이동용이고 상위 섹션을 오가는 동안 계속 보인다, 탭을 숨기거나 비활성화하지 않는다(Apple HIG, S14). 터치 영역 최소 44×44pt(iOS, S15)·48×48dp(Android, S16). 뒤로(Back)와 위로(Up)는 같은 이력을 따르고, 딥링크로 들어와도 직접 들어온 것과 같은 뒤로 경로를 만든다(Android, S17).
- 결제(Baymard, S18): 이탈 이유 1위는 예상 못 한 추가 비용, 그다음 계정 강제 생성, 길고 복잡한 과정, 총액을 미리 못 봄.

## 2. 점검표

형식: 점검 / 확인 방법 / 결함으로 보는 기준 / 근거. 기준에 숫자가 없는 항목은 "개선 요청"이 기본이다.

**한 화면의 목표와 위계**
1. 주요 버튼 하나 / 화면마다 가장 강조된 버튼 수를 센다(DOM의 primary 변형) / 같은 강조의 버튼이 둘 이상이고 무엇을 먼저 할지 모호하면 결함 / One thing per page, NN/g 8
2. 몇 초 안에 화면 목적을 말할 수 있음 / 처음 보는 사람(또는 새 컨텍스트 에이전트에 캡처만 주고)에게 "여기서 뭘 하나"를 묻는다 / 대답이 틀리거나 갈리면 개선 요청, 핵심 흐름 화면이면 결함 / Easy to answer
3. 핵심 정보가 첫 화면에 / 기기 첫 화면 캡처 / 장식 때문에 가격·결과·주요 버튼이 스크롤 아래로 밀리면 개선 요청 / 그래픽 원칙, NN/g 8
4. 가치 먼저, 비용 나중 / 비로그인으로 둘러보기→고르기까지 간다 / 둘러보는 단계에서 로그인·개인정보를 요구하면 결함 / Value first, cost later

**내비게이션(뒤로·하단 탭·깊이)**
5. 화면 뒤로와 시스템 뒤로가 같은 곳으로 / 화면마다 둘 다 눌러 본다 / 도착이 다르거나, 첫 화면이 아닌데 앱이 닫히면 결함 / Android navigation
6. 딥링크·외부 결제에서 돌아온 뒤 뒤로 / 그 경로로 들어와 뒤로 / 빈 화면, 결제창 재진입, 앱 종료면 결함 / Android navigation
7. 하단 탭의 규칙이 하나 / 상위 섹션 사이 이동과 한 단계 들어간 화면을 오간다 / 상위 섹션에서 탭이 사라지면 결함. 어느 깊이에서 탭을 숨길지는 제품 규칙이다 — 규칙이 화면마다 다르게 적용되면 결함, 규칙 자체를 바꾸자는 것은 변경 요청 / HIG tab bars, NN/g 4
8. 선택된 탭이 처음부터 선택 색 / 실제 터치(`touch`)로 탭을 옮긴 직후 색을 읽는다 / 선택 표시가 늦게 나타나거나 다른 상태 색이 덮으면 결함 / NN/g 1
9. 하단 탭 수와 용도 / 탭 개수와 동작 / 2~5개를 벗어나거나 탭이 이동 대신 동작을 실행하면 개선 요청 / 토스 개발자 문서, HIG
10. 나갈 길이 항상 있음 / 모달·시트·웹뷰마다 닫기 / 닫기나 뒤로로 빠져나올 수 없으면 결함 / NN/g 3, 다크 패턴
11. 뒤로를 가로채는 팝업 없음 / 담기·입력 뒤 떠나 본다 / 뒤로를 막고 홍보·동의 시트를 띄우면 결함 / 다크 패턴
12. 같은 입구가 여러 곳에 흩어지지 않음 / 같은 기능(문의, 전체보기 등)으로 가는 입구 수와 위치를 센다 / 같은 일에 서로 다른 모양의 입구가 여럿이면 개선 요청 / One thing per page, NN/g 4·8

**선택과 입력**
13. 선택지 수와 묶음 / 한 화면의 선택지를 센다 / 많은데 검색·묶음·추천이 없으면 개선 요청(고정 숫자 기준은 없음) / Hick
14. 합리적인 기본값 / 첫 진입에서 미리 골라진 값 / 매번 같은 값을 다시 골라야 하면 개선 요청 / NN/g 5, Baymard
15. 터치 영역 / 요소 크기를 잰다 / 44×44pt(iOS)·48×48dp(Android) 미만이면 결함(아이콘 버튼 포함) / HIG, Android
16. 입력 최소화·알맞은 키보드 / 입력칸 수, inputmode·autocomplete / 이메일·숫자 칸에 맞지 않는 키보드, 자동 완성 막힘이면 결함 / Baymard, NN/g 7
17. 탭과 세로 스크롤로 끝남 / 핵심 흐름을 끝까지 / 가로 스와이프·길게 누르기를 해야만 진행되면 결함 / Tap & scroll

**상태 표시(선택·로딩·빈 상태·오류)**
18. 선택 상태가 분명 / 고르고 다음 화면까지 / 색만으로 구분해 모호하거나 다음 화면에 반영되지 않으면 결함 / NN/g 1
19. 반응 지연 / 탭부터 반응까지 잰다 / 400ms 넘는데 피드백이 없으면 개선 요청, 2초 넘게 무반응이면 결함 / Doherty, 토스 개발자 문서
20. 빈 상태 / 목록이 비었을 때 / 빈 칸만 있거나, 불러오는 중에 "없음"이 보이거나, 다음 행동 버튼이 없으면 결함 / NN/g 빈 상태
21. 오류 메시지 / 네트워크 끊기·취소·잘못된 입력 / 코드만 보이거나, 원인·해결이 없거나, 입력값이 사라지면 결함 / NN/g 오류, Baymard
22. 그래픽이 실제 상태와 맞음 / 성공·실패·빈 화면의 아이콘 / 성공인데 경고 아이콘, 기다릴 일 없는데 로딩이면 결함 / 토스 그래픽 원칙

**문구**
23. 결과를 예상할 수 있는 버튼 이름 / 이름과 실제 결과를 비교 / 다르거나 "확인"만 있어 결과를 알 수 없으면 결함 / Predictable hint
24. 쉬운 말 / 화면 문구를 모은다 / 설명 없는 전문 용어는 개선 요청, 핵심 단계(설치·결제)의 이해를 막으면 결함 / Casual concept, Easy to speak
25. 말투와 표기 일관 / 문구 전체를 검색 / 합니다체·해요체 혼용, 같은 말의 띄어쓰기 차이, 거절 버튼 "취소", 강요·공포 문구는 개선 요청 / 토스 라이팅 규칙

**일관성**
26. 같은 개념은 같은 말·같은 부품 / 화면 사이 용어·버튼 모양·위치 대조 / 같은 동작의 이름·모양·위치가 화면마다 다르면 결함 / NN/g 4, Jakob

**결제·전환**
27. 총액을 먼저, 마지막에 새 비용 없음 / 담은 금액과 결제 금액 비교 / 결제 직전에 처음 보는 비용이 생기면 결함 / Baymard, 존중(Respect)
28. 결제 뒤 다음 할 일이 바로 보임 / 완료 화면 / 완료 여부가 모호하거나 다음 단계(사용 안내 등)로 가는 길이 없으면 결함 / NN/g 1

## 3. 어떻게 시험하나

- 기기에서 실제 터치로 본다. 선택·hover·누름 상태는 JS 클릭으로 재현되지 않는다([device-qa](../../device-qa/SKILL.md)의 `touch`).
- 신고에 플랫폼이 없으면 Android와 iOS를 둘 다 본다.
- "몇 초 안에 이해" 항목은 이 실행에 참여하지 않은 새 컨텍스트에 캡처만 주고 묻는다(같은 컨텍스트는 이미 답을 안다).
- 숫자 기준(터치 영역, 지연, 탭 수)은 측정값을 증거로 남긴다.
- 문구는 화면에서 모은 원문을 그대로 적는다(고친 안은 따로).

## 4. 분류와 심각도

| 분류 | 기준 | 어디로 |
|---|---|---|
| 결함 | 2절의 결함 기준·플랫폼 규칙·금지 다크 패턴을 어김, 사용자가 일을 못 끝내거나 잘못 끝내거나 돌아오지 못함, 화면이 실제 상태와 다름, 명세·수용 기준과 다름 | 결함 카드 |
| 변경 요청 | 끝낼 수는 있지만 원칙에 비춰 더 단순해질 여지가 분명함, 또는 명세가 지금 동작을 정해 둠 | 변경 요청(명세 갱신 필요 표시) |
| 취향 | 출처 없는 미감 판단(색이 별로, 아이콘이 더 예쁨) | 보고하지 않거나 참고 |

- 먼저 명세(화면 구조·기능 요구)가 지금 동작을 정해 두었는지, 관리자 데이터로 바뀌는 것인지 확인한 뒤 코드 위치를 찾는다.
- 심각도: [severity.md](severity.md)를 따른다. 화면 문제는 대개 low~medium이다. 돈·상태를 잘못 알게 하는 화면(실패를 성공처럼, 총액 숨김)은 high 이상, 결제·설치·환불 길이 막히면 critical 후보.
- 증거: 화면 경로, 기기·OS·빌드, 번호 붙인 단계, 캡처, 사용자가 기대할 것 한 문장, 어긴 원칙 이름과 출처 번호, 측정값. **원칙 이름만 있고 재현 근거가 없으면 올리지 않는다.**
